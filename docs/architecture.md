# Builderella architecture

Builderella turns the computers you already own, plus rented or temporary
cloud machines, into one build-and-test pool for coding agents. An agent
submits an immutable snapshot of its working tree and a task. The fleet picks
a compatible machine, reserves resources, queues when it must, runs the whole
build → run → test → cleanup lifecycle, returns attributable results, and
only then frees the resources.

This document is the contract every crate is built against. Wire types live
in `crates/bella-core`; where this document and `bella-core` disagree,
`bella-core` wins and this document gets fixed.

## 1. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D1 | Rust workspace, one binary `bella` with roles (`controller`, `worker`, client commands, `mcp`). MSRV 1.89, edition 2024. | One file to install per machine. macOS Monterey on Intel is a supported host, so the MSRV is pinned to a toolchain that still installs there. |
| D2 | Controller state in embedded SQLite (WAL, `synchronous=FULL`, foreign keys on). One controller process is the only writer and the only scheduler. | v1 has no high availability, so a networked database buys nothing and costs a service to install, back up and version on every controller OS. Persistence sits behind `bella-ledger`; a PostgreSQL backend can replace it when a standby controller is added. |
| D3 | No Redis or other broker in the control plane. | The queue is rows in the ledger. Losing a cache must never make the fleet forget that a build is running. |
| D4 | Each worker keeps its own SQLite recovery journal on local disk. | A worker must recover process ownership and unfinished cleanup after a restart, with the controller unreachable. |
| D5 | HTTPS REST plus server-sent events for clients; one worker-initiated WebSocket per worker for control. TLS is on by default with a fleet certificate generated by the controller and pinned by SHA-256 fingerprint at pairing. | Workers need no inbound port. No VPN product is required, and pinning avoids running a public CA for a LAN. Plain HTTP is allowed only on loopback or with an explicit flag. |
| D6 | Source and artifacts are content-addressed objects named by the SHA-256 of their uncompressed bytes, zstd-compressed at rest and in transit, on the controller's filesystem. File-level deduplication. | The object store interface is independent of the scheduler; S3/GCS backends slot in later. |
| D7 | Recipes live in `builderella.toml` at the project root. | TOML has a maintained Rust parser with good error spans. |
| D8 | Execution is native processes inside one containment scope per attempt: cgroup v2 on Linux, Job Objects on Windows, process groups on macOS. Each adapter reports what it verified as `hard` or `advisory`. Containers and VMs are later executors. | Native toolchains (Xcode, MSVC) are the point. macOS has no cgroup-equivalent, so its protection is labelled advisory everywhere it is shown. |
| D9 | v1 places a whole job on one machine and reserves its peak simultaneous envelope: services that coexist are summed, phases that do not overlap take the maximum. | Prevents the app taking the last slot its own tests need, without gang scheduling across hosts. |
| D10 | The agent interface is a local stdio MCP server (`bella mcp`) plus the same operations in the CLI. The MCP server is hand-written JSON-RPC with no SDK dependency. | Capture must read the author's worktree, so the bridge has to be local. The MCP subprocess owns no build lifetime: closing it cancels nothing. |
| D11 | Cloud capacity is modelled end to end (durable intentions, budget holds, overflow policy, janitor health) against a provider contract with a simulated provider. Real AWS and GCP adapters are not part of v0.1, and paid provisioning stays off until an administrator supplies accounts and allowances. | Spending real money needs real limits that only the owner can set. The ledger and policy logic are testable without them. |
| D12 | Dashboard is React + TypeScript built to static files and embedded in the controller binary. | No frontend server on enrolled machines. |
| D13 | Bearer tokens (admin, developer, viewer, machine) stored as hashes. Machines join with a single-use, short-lived pairing code. | An ordinary agent can submit and cancel; it cannot lower a workstation reserve, raise a cloud allowance or enroll a machine. |

Scope boundaries for v0.1: whole commands and explicit step graphs are
scheduled, not individual compiler invocations. One task needs one machine
with enough memory; RAM is never pooled across machines. Shared-service
adapters (pooled PostgreSQL/Redis with per-environment roles), container and
VM executors, GUI/device runners, signing lanes, real cloud providers and
automatic worker updates are out of scope and listed in §9.

## 3. Lifecycle and ownership

```
Capturing → Queued → Offered → Preparing → Executing → Collecting → Cleaning → Finished
                ▲        │                                   │
                └────────┘ rejected/revoked before start     └→ Quarantined ⇄ Cleaning
```

The handshake never holds a database transaction open while waiting for a
worker:

1. **Reserve.** In one transaction the controller picks a job, creates the
   attempt with the next generation and reserves the resources on the chosen
   machine. The capacity check runs inside this transaction.
2. **Offer.** The worker checks fresh local capacity and policy, journals a
   held reservation and replies. It executes nothing.
3. **Start committed.** The controller rechecks epoch, generation,
   cancellation and reservation ownership, persists the start permit, then
   sends `Start`. From this commit on, the attempt is assumed to be running,
   acknowledgement or not.
4. **Run.** The worker journals the permit, creates the scope, materializes
   the snapshot and launches. A retransmitted `Start` cannot launch twice.
5. **Release.** Resources return to the pool only when the worker reports a
   release proof (scope verified empty, workspace removed) or isolation is
   otherwise proven, e.g. the machine rebooted.

Release gates. Each is a test somewhere in the workspace:

* A start permit is durable before execution.
* A lost acknowledgement still counts as potentially running work.
* A disconnect does not prove termination. Stale after 15 s, unreachable
  after 30 s; neither releases a reservation.
* Resources stay owned until cleanup is confirmed. Unverifiable cleanup
  quarantines the capacity.
* A job has at most one live or unresolved attempt.
* Only the current generation can set a job's canonical result.
* Cancel is a request followed by observed cleanup.
* A release is applied at most once; capacity never goes negative.
* The same idempotency key returns the same job; the same key with a
  different body is an error.
* A restarted controller bumps its epoch and reconciles with each worker
  before offering it new work.

## 4. Resources and admission

A slot is a `ResourceVector`: CPU in milli-CPUs, memory, scratch disk, and
named tokens for countable things (simulators, GUI sessions, service
quotas). One physical host has one budget; guests divide it.

The controller owns durable reservations. The worker makes the final local
decision from fresh observations. For a request `q` on a host with policy
ceiling `C`, grants `r_i` with measured use `u_i`, available memory `A`,
floor `F` and guard `G`:

* **Policy capacity:** `Σ r_i + q ≤ C` in every dimension.
* **Immediate safety (memory):** `A − F − G − Σ max(r_i − u_i, 0) ≥ q.memory`.
  Offered and start-authorised attempts count with `u_i = 0`.

Low observed use never shrinks a promise. Observed excess is charged at
once and triggers remediation. Suspending a process frees no memory.

The protected-workstation profile withholds at least 20% of CPU and
max(20% RAM, 4 GiB) for the foreground, keeps 2 GiB available, runs managed
work at low priority, allows one heavy job, and never borrows the reserve.
On macOS this is admission policy plus pressure response, labelled
`advisory`. The local loop keeps running when the controller is unreachable.

## 5. Platform model

Four separate fields, never one platform string: build host, artifact
target, test runtime, additional capabilities. A recipe that declares no
build hosts is pinned to the platform that submitted it. `Any` means any
combination the recipe validated. Capabilities carry exact versions and a
state (installed, missing, unhealthy, occupied, unauthorised, unverified),
and every exclusion produces a specific reason.

## 6. Crate contracts

Common rules are in `AGENTS.md`. Each crate lists the acceptance scenarios
(`A01`…`A68`, see §8) it must cover with tests.

### 6.1 bella-store

`FsStore::open(root)` implementing `bella_core::store::ObjectStore`.

* Layout: `objects/<2 hex>/<digest>` zstd-compressed, temporary files under
  `tmp/` with a unique name per put. Publish by fsync + atomic rename +
  directory fsync. A crash leaves only stale temporaries.
* `put` hashes the bytes it retains while writing them. A digest mismatch
  or an over-limit object publishes nothing. Concurrent puts of the same
  object are safe.
* `open` verifies content against the digest and stops at the recorded
  size, so a corrupt or bomb-like file is an error, never output.
* `size` is O(1).
* `put_compressed` / `open_compressed` move already-compressed bytes for
  HTTP transfer; `put_compressed` verifies by decompressing as it stores.
* `gc(is_live, grace)` deletes unreferenced objects and stale temporaries
  older than `grace`, re-checking liveness immediately before each delete.
  `stats()` reports object count and bytes.
* A re-put of a stored object reads its header only. `verify(digest)`
  reads one object in full; `repair(digest, bytes)` and
  `repair_compressed` replace a stored copy that fails it, and
  `remove(digest)` deletes one object unconditionally. Both take the
  publish lock the way `gc` does.
* Covers: A31 (no temp collision), A36 (corrupt blob rejected), A46 (pinned
  objects survive GC).

### 6.2 bella-capture

`capture(roots, policy, store, barrier) -> CaptureResult { manifest,
snapshot_id, meta, stats, excluded_secrets, warnings }`. `roots` is one
`RootSpec { path, mount }` per source root, `policy` a `CapturePolicy` and
`barrier` an optional `CaptureBarrier`. `capture_with_clock` also takes the
clock that stamps `meta.captured_at`.

* Git roots: enumerate with `git ls-files -z` (tracked, plus untracked
  non-ignored by policy), then read **working-tree bytes**. Never touch the
  index, stash, HEAD or any ref. `.git` is never captured.
* Non-git roots: walk the directory with the exclude rules.
* Each file is read once into a bounded spool while hashing; those spooled
  bytes are what is stored. A file whose size or mtime changed across the
  read is retried a bounded number of times, then the capture fails. A
  final re-stat pass detects edits made during the capture.
* Consistency: `Coordinated` when a `CaptureBarrier` was acquired,
  otherwise `BestEffort`. A policy that requires more than was achieved
  fails the capture.
* Secrets: paths matching the secret patterns (defaults include `.env`,
  `.env.*`, `*.pem`, `*.key`, `id_rsa*`, `.npmrc`, `.netrc`) are excluded
  and reported when untracked, and fail the capture when tracked unless
  explicitly allowed. Git-ignore status alone is never the secret policy.
* Ignored files are included only when declared; a declared input that is
  missing fails the capture.
* Symlinks are recorded as links. Each target is checked with
  `bella_core::snapshot::validate_symlink`, and the finished manifest with
  `Manifest::validate`, which also follows links through each other. An
  absolute target, a target that leaves its root, and a chain of links
  that does, all fail the capture with an error naming the link.
  Executable bits are recorded (from the git index on Windows).
* Unhydrated LFS pointers, uninitialised submodules and sparse checkouts
  with missing required paths fail with a precise message. Initialised
  submodules are captured from their working trees.
* Paths that are not valid UTF-8 fail with the offending path; Unicode,
  spaces and newlines in names are preserved exactly.
* `meta` records Windows incompatibility
  (`bella_core::snapshot::windows_incompatibility`), case/normalisation
  collisions and symlink presence so the scheduler can exclude unsuitable
  executors.
* Multiple roots are captured under one barrier into one manifest.
* Covers: A26, A27, A28, A29, A30, A31, A32, A33, A34, A35, A37.

### 6.3 bella-materialize

`materialize(manifest, store, dest, options) -> MaterializeReport`,
`check_platform(manifest, os, case_sensitive)`,
`verify_tree(manifest, dest)`, `remove_tree(path)`,
`is_case_sensitive(dir)`.

* Validates the manifest first with `Manifest::validate`, which includes
  following symlinks through each other; a chain that leaves its root is
  reported as `SymlinkEscapes`. `dest` must be absent or empty.
* Files are written with `create_new`, never through a symlink; symlinks
  are created last. Nothing is hard-linked from a cache.
* Sizes and digests are checked while writing; any failure removes the
  partial tree and returns an error.
* Windows-incompatible names (the rules of
  `bella_core::snapshot::windows_incompatibility`), over-long paths, case
  collisions on a case-insensitive volume and unsupported symlinks are
  precise errors; source is never renamed.
* `remove_tree` never follows links and copes with read-only files.
* Covers: A27, A28, A29, A36.

### 6.4 bella-recipe

Parses `builderella.toml`, validates it and resolves one recipe plus
overrides into a `JobSpec`. Also builds an ad-hoc `JobSpec` for a bare
command, pinned to the origin platform. File format: `docs/recipes.md`.

* Step graph validation: unique names, known dependencies, no cycles,
  services declare readiness, cleanup steps have no dependants.
* Envelope: peak = Σ service step resources + max over the other steps,
  never below the recipe-level declaration. `initial ≤ peak ≤ maximum`.
* Human units (`8GiB`, `30m`), precise errors with file positions.
* `recipe_digest` covers everything that affects the result and excludes
  priority and placement.
* Policy limits clamp or reject; a recipe cannot widen fleet or machine
  policy.
* Covers: A19 (combined envelope), A38/A39 (the four platform fields reach
  the spec intact).

### 6.5 bella-ledger

`Ledger::open(path, clock)` / `open_in_memory(clock)`. Synchronous API;
callers use a blocking thread. Opening bumps and returns the controller epoch and refuses
a newer schema. Every transition writes its event row in the same
transaction.

Required operations: principals and token authentication; pairing codes
(single use, expiring); machines (enroll, inventory, policy revisions,
heartbeat observation, lifecycle); projects; snapshots; `submit_job` with
idempotency; `create_offer` (creates the attempt and reservation after
checking, inside the transaction, that the job is queued, has no unresolved
attempt and that the machine's held reservations plus the request fit the
capacity the caller passes); `record_offer_reply`; `revoke_offer` (only
without a start permit); `commit_start`; generation-fenced attempt events;
exactly-once `record_release`; `request_cancel`;
`mark_machine_uncertain`; `expire_offers`; retries by retry class; environments and leases; logs
(idempotent append by stream offset, bounded pages by cursor, truncation
marker); artifacts; `events_after`; queue and fleet queries;
`reconcile(machine, boot_id, reports) -> verdicts`.

Reconcile rules: current generation with a start permit → `Continue`;
offer without a start permit → revoke and `Forget`; unknown, stale or
cancel-requested → `Abort`. An attempt the ledger holds that the worker no
longer reports is released as `InfraInterrupted` when the boot id changed
(processes cannot have survived) or when no start permit was delivered;
otherwise it stays held and uncertain.

`with_transaction` and component-scoped migrations
(`apply_component_migrations`) let `bella-cloud` keep its tables in the
same database.

* Covers: A01, A02, A04, A11, A12, A13, A14, A15, A60, A61 at the
  persistence level.

### 6.6 bella-scheduler

Pure: `schedule(&FleetState) -> Schedule { offers, reasons }`,
`explain(state, job)` for a queued job, `evaluate(state, job)` for one
that is not queued yet (planning a submission), `job_blocker(state, job)`
and `effective_capacity(ceiling, budget)`. No clock, no I/O; `now` is
input.

* Eligibility with permanent versus temporary blockers: platform (origin
  pin, build hosts, test runtime), placement choice, capabilities,
  snapshot/platform incompatibility, project allow-list, LAN-only source,
  machine flags, freshness, capacity `min(ceiling, effective budget) −
  reserved`, concurrency limits, unresolved previous attempt. Named tokens
  follow the capacity rule too: the worker's budget names every token its
  policy declares, and a token it does not name is not granted.
* Ordering: weighted service across priority bands so lower bands always
  progress; weighted fair share across projects by dominant reserved share;
  sessions and accounts add no weight; bounded aging.
* Backfill: small jobs may pass a large one unless it has waited past the
  starvation threshold, after which one eligible machine stops admitting
  other work until the large job fits (`ReservedForOlderJob`).
* Placement: prefer machines that are not protected workstations for
  portable work, keep scarce capabilities free, then most headroom.
  Deterministic tie-breaks. Offers within one call never double-book.
* Covers: A01, A02, A09, A10, A19, A38, A39, A40, A55.

### 6.7 bella-probe

`inventory(worker_version, executors, previous)` (`inventory_with` adds
`ProbeOptions`), `detect_capabilities(options)`, `hardware()`, `os_info()`,
`Sampler::new(work_dir)` with `sample(managed) -> Telemetry`, `boot_id()`,
`hostname()`.

* Read-only: never changes PATH, selected Xcode, or any installation.
* Every external probe has a timeout. Missing tools are simply absent.
* Capabilities carry exact versions; a present but unusable tool (Docker
  daemon down) is `unhealthy`.
* Telemetry normalises OS counters and sets `quality` honestly.
* Idle sampling cost stays under 1% of one CPU.

### 6.8 bella-contain

The `Containment` and `Scope` traits are defined in `lib.rs`. One module
per OS implements them. `self_test` must actually exercise descendant
containment and each limit and downgrade what did not work.

* Covers: A11 (one tree per scope), A16 (PID reuse), A24 (daemon outlives
  root), A66 (hidden descendants), on each OS with its real guarantee.

### 6.9 bella-journal

`Journal::open(path, clock)`, and `open_existing` for a tool beside a
running worker: identity and counters, attempts with validated
local-state transitions, an event outbox with gap-free sequences and
acknowledgement, seen-command results for idempotency, log offsets,
`recover(current_boot)`, `held_resources()`. `synchronous=FULL`, plus a
reserve file released on disk-full so recovery records can still be
written. The enrollment is recorded once; `set_controller_endpoint(url,
fingerprint)` follows a controller that moved without enrolling again.

* Covers: A11, A13, A16, A17 at the journal level.

### 6.10 bella-protect

Pure: `budget(input) -> Budget`, `admit(input, request)`,
`actions(input, history)` (also exported as `pressure_actions`).
Implements §4, power and thermal rules, pause/drain/boost, and eviction
choice with hysteresis. `Budget.ceiling` always carries every token the
policy declares at its declared count, which is what the scheduler's
capacity check relies on.

* Covers: A04, A05, A06, A07, A08 (no controller input needed), A65.

### 6.11 bella-net

Server identity generation and loading, fingerprint, rustls server config,
fingerprint-pinned client config (signatures still verified), token
minting and hashing with constant-time comparison, pairing codes, the
enrollment string, private-file writes.

### 6.12 bella-mcp

`serve(input, output, fleet: Arc<dyn FleetOps>, options)`. Tools:
`plan_job`, `submit_job`, `get_job`, `wait_job`, `read_logs`, `cancel_job`,
`get_artifacts`, `get_environment`, `renew_environment`,
`finish_environment`, `explain_queue`, `list_fleet`.

* A job id comes back quickly; `wait_job` is bounded and a timeout cancels
  nothing. End of input cancels nothing.
* Workspace paths must be inside the configured allowed roots.
* Results are compact and bounded; log text is marked untrusted. With a
  dashboard URL configured, job results link to `<url>/#/jobs/<id>`.
* Covers: A21, A61.

### 6.13 bella-cloud

Provider trait, `SimProvider` with fault injection, the intention state
machine, atomic budget holds, reconciliation, janitor-health gate and the
pure overflow policy with hysteresis and launch limits.

* Covers: A48, A49, A50 (modelled), A51, A52, A53, A54, A55, A56.

### 6.14 dashboard

Five views: Fleet, Queue, Job, Environments, Administration. Reads the REST
API and the event stream. Shows measured use, reservations, external
activity and the protected foreground share as separate bars, and the
enforcement strength per machine. Nothing beyond those views.

### 6.15 bella-client

Typed async client for every route in `bella_core::api`, built on the
pinned TLS configuration from `bella-net`.

* One method per route, returning the `bella_core::api` type or an
  `ApiError`. Transport failures are distinct from API errors.
* `events(after)` yields `EventRecord`s from the event stream and
  reconnects from the last sequence it saw.
* `HttpObjectStore` implements `ObjectStore`: it asks which digests are
  missing before uploading, sends and receives zstd-compressed bodies, and
  verifies every download against its digest. It is called from blocking
  threads.
* Retries are bounded, with exponential backoff and jitter, and only for
  requests that are safe to repeat. `submit_job` always carries an
  idempotency key.

### 6.16 bella-controller

One process: HTTP API, worker hub, dispatch loop, object store, embedded
dashboard. `Controller::start(config)` is a library call so tests run it
in-process on port 0.

* Data directory: `ledger.sqlite`, `objects/`, `logs/`, `tls/`, and an
  admin token created on first start and written to a private file.
* Every route authenticates a bearer token through the ledger and checks
  the role. Enrollment attempts are rate limited.
* Snapshot registration validates the manifest, confirms every referenced
  object is stored, stores the manifest itself as an object, then registers.
* Worker hub: `Hello` → `ledger.reconcile` → `Welcome` + `Reconcile`. No
  offer goes to a machine before its reconcile. Events and logs are
  acknowledged only after they are durable. Control messages are never
  queued behind log acknowledgements.
* Dispatch: on a tick and on change, build a `FleetState` from the ledger,
  call `bella_scheduler::schedule`, and for each planned offer run the
  handshake of §3. Sweeps: offer expiry, authority renewal, stale and
  unreachable marking, cancellation fan-out, environment lease expiry,
  retries, object-store garbage collection from `ledger.live_digests()`.
* A start bumps the epoch. A machine is excluded from scheduling until it
  has reconnected and reconciled.
* Covers end to end: A01, A02, A12, A13, A14, A15, A21, A22, A37, A59, A60, A61.

Wire details the client and the controller share:

* **Authentication.** `authorization: Bearer <token>` on every route except
  `GET /healthz` and `POST /enroll`, which carries the pairing code in its
  body. The worker WebSocket upgrade request carries the machine token the
  same way.
* **Errors.** A non-2xx response has a JSON `ApiError` body and the status
  from `ErrorCode::http_status`.
* **Objects.** `PUT /objects/{digest}` with
  `content-type: application/vnd.builderella.object` carries the
  `bella_store::format` encoding (header plus one zstd frame) and is stored
  with `put_compressed`; with `application/octet-stream` it carries the raw
  bytes. Either way the controller verifies the digest before publishing
  and answers `204`, or `409` with `ApiError` on a mismatch. An object that
  already exists is `204` without reading the body further.
  `GET /objects/{digest}` answers with the stored encoding and
  `content-type: application/vnd.builderella.object`; `?raw=1` answers with
  the decoded bytes as `application/octet-stream`.
* **Snapshots.** The controller stores the manifest's canonical bytes as an
  object; its digest is the snapshot id and `manifest_digest`.
* **Idempotency.** `POST /jobs` reads the `idempotency-key` header.
* **Long poll.** `GET /jobs/{id}/wait` holds for at most 60 s.
* **Events.** `GET /events` is `text/event-stream`. Each event has
  `id: <seq>`, `event: <kind>` and `data: <EventRecord JSON>`. With
  `?after=<seq>` (or a `last-event-id` header) the stream first replays
  everything after that sequence; without it, only events from now on are
  sent. A comment line is sent every 15 s as a keep-alive.
* **Worker socket.** Text frames, one JSON `WorkerMsg` or `ControllerMsg`
  each. The first frame from the worker is `Hello`; the controller answers
  with `Welcome` and then a `Reconcile` command. WebSocket ping/pong is
  used for liveness in addition to heartbeats.
* **Dashboard.** Served at `/` with fragment routes (`/#/jobs/<id>`), so
  only `index.html` and `assets/` need serving.

### 6.17 bella-worker

One process per physical machine.

* `enroll`: probe, exchange the pairing code for a machine id and token,
  store the token in a private file and the rest in the journal.
* Connection loop with backoff and jitter; `Hello` carries the journal's
  reports; verdicts are applied before anything else.
* Protection loop every second: sample, compute the budget, apply actions.
  It runs whether or not the controller is reachable.
* Offer: check epoch and policy revision, `bella_protect::admit`, journal
  the hold, reply. Start: `journal.authorize_start`; only `Fresh` launches.
* Runner per attempt: fresh workspace, scope created and journaled before
  the first spawn, snapshot materialized through a local object cache,
  steps in dependency order (tasks and tests one at a time, services in the
  background with readiness probes), logs spooled to disk and streamed with
  offsets and a truncation marker at the allowance, artifacts uploaded then
  announced, outcome reported, cleanup steps run, scope stopped and
  verified empty, workspace removed, release proof sent. Anything that
  cannot be verified is quarantined.
* Steps get a minimal environment: system essentials, `BELLA_*` variables,
  then the recipe's and the step's. Nothing else from the worker leaks in.
* Authority: past `valid_until` plus the permitted disconnected time, or
  past the hard deadline, the worker stops the attempt on its own.
* Restart: attempts from an earlier boot are lost and released once their
  workspace is gone. Attempts from this boot are re-adopted by scope and,
  in v0.1, stopped and reported as interrupted, because their output pipes
  cannot be recovered.
* Local pause, resume and drain are written to the journal by the CLI and
  picked up by the running worker, so they work offline.
* Covers end to end: A05, A07, A08, A11, A16, A17, A19, A24, A25, A47, A66.

### 6.18 bella-cli

The `bella` binary. `bella controller …`, `bella worker …`, `bella login`,
`submit`, `plan`, `jobs`, `job`, `wait`, `logs`, `cancel`, `artifacts`,
`explain`, `env …`, `fleet`, `queue`, `machine …`, `project …`, `token …`,
`mcp`. Output is plain text by default and JSON with `--json`. A failed job
makes `submit --wait` exit non-zero; a wait timeout never cancels.

### 6.19 bella-service

Installs, removes, inspects and runs the controller and worker as operating
system services; `bella controller service …` and `bella worker service …`
call it. `render(spec, os)` is pure and covers every platform on every host;
`install`, `uninstall`, `status`, `start` and `stop` act on the host's
manager. `ShutdownSignal` is the stop request, and on Windows
`run_as_service(name, body)` speaks to the Service Control Manager.

| Host | Definition | Account |
| --- | --- | --- |
| Linux | systemd system unit; a user unit as the second option (boot start needs lingering) | a system worker names its user; the controller defaults to root |
| macOS | LaunchAgent in the graphical session; the controller may be a LaunchDaemon | the logged-in user for the worker, which is never a daemon |
| Windows | real service, automatic start | `LocalSystem` for the controller; the worker's account is named by the caller |

* Services restart after a crash or a non-zero exit and stay down after a
  clean exit or a requested stop.
* A stop gets the cleanup timeout plus the terminate grace plus 30 s.
* Linux workers get `Delegate=yes` (§6.8), `OOMPolicy=continue` and
  `KillMode=mixed`. The Windows worker stays in session 0, where its job
  objects are found again after a restart.
* Windows services have no standard output and no working directory
  setting: the definition passes both directories in the environment,
  `run_as_service` changes to the working one, and the program writes its own
  log files. macOS logs to files in the log directory, Linux to the journal.
* The worker's account must own its data directory, work root and
  toolchains. On Windows an ordinary account also needs its password and the
  "Log on as a service" right.
* Installing the same specification twice changes nothing; a different one
  needs an explicit replacement. Only definitions this crate wrote are
  replaced or removed.
* Environment keys that look like secrets are refused.

## 7. Timing defaults

See `bella_core::defaults`. Protection loop 1 s, heartbeat 5 s, stale 15 s,
unreachable 30 s, offer expiry 15 s, authority window 60 s renewed every
10 s, terminate grace 10 s, environment idle 15 min / lease 30 min / maximum
4 h. All are starting values to tune per machine.
